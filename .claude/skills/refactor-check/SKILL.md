# リファクタリングを始めるかどうかの判定

リファクタリングは「やったほうがよさそう」で始めない。判定スクリプトの結果で決める。

## 1. 判定する

機能の実装や修正が一区切りついたら、変更したファイルを調べる。

```bash
python checks/refactor_check.py --changed --json
```

ユーザーが場所を指定したときは、その場所を調べる。

```bash
python checks/refactor_check.py src/orders --json
```

## 2. 判定に従う

| `verdict` | やること |
|---|---|
| `act` | 今の作業を止めて、`high` の項目をユーザーに見せる。直す手順を提案し、了承を得てから直す |
| `suggest` | 今の作業は続ける。作業の報告の最後に `medium` の項目を一覧で見せ、直すかどうかを聞く |
| `skip` | 何も直さない。`low` の項目は報告もしない(ユーザーに聞かれたら見せる) |

`skip` のときに「ついでに整理しました」をしない。頼まれていない整理は、差分を読みにくくする。

## 3. 直す前に確かめる

`next_steps` の先頭に `P01` や `P03` があれば、コードを直す前にそれを先に片づける。

- `P01`(テストがない): 直す部分の今の動きを固定するテストを先に書く。バグのように見える動きも直さず、今の結果をそのまま期待値にする
- `P03`(コミットしていない変更がある): 先にコミットするようユーザーに頼む。機能の変更と整理を同じコミットに混ぜない

## 4. 直す

- `findings` の `catalog_id` を `catalog.md` で引き、「こう直す」に従う
- 1種類ずつ直す。1つ直すたびにテストを実行し、通ってから次に進む
- 動きは変えない。途中でバグを見つけても直さず、最後にまとめて報告する
- 外から呼ばれる関数の名前・引数・戻り値は変えない。変える必要があるときは、先に呼び出し元を全部挙げてユーザーに確かめる
- `findings` にないファイルは触らない

## 5. スクリプトが見つけられない項目

カタログで判定が「AI」になっている項目(R03 名前、D08 既存の処理の作り直し、E03 備えすぎ など)は、スクリプトでは検出できない。変更したコードを自分で読み、当てはまるものがあれば `suggest` と同じ扱いで報告する。

特に、自分が今書いたコードについて次の3つを確かめる。

1. 同じことをする関数が、すでにプロジェクトの中にないか(D08)
2. 起きるはずのない場合に備えた try/catch や空の確認を足していないか(E03)
3. コードをなぞるだけのコメントを書いていないか(R15)

## 6. 終わったら

もう一度判定を実行し、直した項目が消えたことを確かめる。報告には次を入れる。

- 直した項目(カタログのID)と、直さなかった項目とその理由
- テストの結果
- 途中で見つけたが直さなかったバグ
